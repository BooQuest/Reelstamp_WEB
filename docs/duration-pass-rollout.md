# 기간제 이용권 적용 및 검증

이번 변경은 DB 상품 조회, 서버 가격 확정, 일회성 결제 요청, 결제 통보, 이용기간과 환불 처리 및 UI를 연결합니다. 기본 판매 상태는 CLOSED입니다. DB 적용·배포·커밋은 사용자가 직접 진행하며, 실제 거래 검증의 진행 상황은 아래에 구분합니다.

## 현재 진행 상태 (2026-10-05 기준)

아래 환경 적용 및 화면 확인 결과는 사용자가 공유한 내용을 기준으로 기록했습니다. 실제 결제 승인 완료를 의미하지 않습니다.

| 항목 | 확인된 상태 |
|---|---|
| 상품 DB | `subscription_plans` 컬럼 확장과 PASS 상품 4개 교체 완료. 기존 상품 DELETE/INSERT는 재실행하지 않음 |
| 개발 DB 신규 테이블 | 사용자가 `pass_orders`, `pass_grants`, `pass_payment_events` 생성 및 검증 쿼리 실행 완료 |
| 기존 기록 | `subscriptions`, `payment_histories`의 기존 데이터 보존 |
| 개발 환경 | 개발 WEB·백엔드에 결제 흐름 반영, TEST_ALLOWLIST 계정으로 구매 진행 확인 |
| 테스트 상품 | 사용자 설정 기준 `PASS_7D`는 1주일 체험권 test, 1,000원·7일. 4,900원 복원은 아직 확인되지 않음 |
| PayApp 결제창 | WEB의 `X_INTERNAL_SECRET`과 개발 백엔드의 `INTERNAL_API_SECRET` 값을 일치시킨 후 결제창 진입 확인 |
| 실제 거래 | 사용자가 아직 결제 승인을 시도하지 않았다고 공유함. 승인·통보·이용권 부여·환불의 실제 거래 검증은 미완료 |
| 운영 환경 | 운영 DB 적용·배포·거래 검증 여부는 확인되지 않음 |

개발 환경에서 확인된 문제와 조치:

- `relation "pass_orders" does not exist`: 신규 테이블 적용 전 발생했으며, 이후 사용자가 신규 테이블 3개를 생성했습니다.
- 주문이 `CREATING` 상태이고 `payment_no`, `pay_url`이 NULL로 남은 채 결제 확인 지연 표시: 내부 인증키 값을 맞춘 후 PayApp 결제창이 열리는 것을 확인했습니다. 이전에 남은 주문의 복구·미결제 요청 정리 여부는 별도로 확인해야 합니다.

다음 단계는 개발 환경의 PayApp 결제창에서 1,000원 승인을 진행하고, 결제 통보 수신·주문 PAID 반영·이용권 부여·결제 내역을 대조하는 것입니다. 이후 환불과 아래 추가 검증을 진행합니다. 테스트 종료 후 판매 중지·커버 복원·테스트 가격 복원 여부도 확인합니다.

## 적용 순서

아래는 환경별 적용 절차입니다. 개발 DB의 상품 교체와 신규 테이블 생성은 이미 완료했으므로 재실행하지 않습니다. 아직 적용하지 않은 환경에서는 해당 환경의 실제 상태를 먼저 확인합니다.

1. Backend `reelstamp-api/docs/sql/20260930_pass_preflight.sql`을 사용자 DB에서 조회합니다. 현재 상품은 ID 1~4의 PASS_7D / PASS_1M / PASS_3M / PASS_1Y, 다음 ID 5입니다. 이미 완료한 상품 DELETE/INSERT는 반복하지 않습니다. 예상하지 못한 참조·트리거가 있으면 여기서 중단합니다.
2. DB 백업 후 Backend `reelstamp-api/docs/sql/20260930_pass_records.sql`을 실행합니다. 신규 테이블 3개만 생성합니다. 기존 상품·구독·결제 내역을 변경하지 않습니다. 이 SQL은 새 코드 배포 전에 필요합니다.
3. Backend 설정을 적용하고 빌드/배포합니다. `PASS_SALES_MODE=CLOSED`가 기본값입니다. `TEST_ALLOWLIST` 검증 시에는 `PASS_TEST_USER_IDS=사용자ID,사용자ID`를 지정합니다. `PASS_TEST_PRODUCT_CODES=PASS_7D`로 테스트 상품을 제한합니다(기본값도 PASS_7D). 허용 계정이라도 목록에 없는 상품은 서버가 구매를 거부합니다. `OPEN`은 일반 판매이며 활성 기간제 상품 전체를 대상으로 합니다. 베타 설정 `REELSTAMP_BETA_ENABLED`와는 독립적입니다.
4. WEB에 `PAYAPP_USERID`, `PAYAPP_LINKKEY`, **`PAYAPP_LINKVAL`**, `X_INTERNAL_SECRET`, `NEXT_PUBLIC_BASE_URL` 및 기존 백엔드 주소 설정이 필요합니다. X_INTERNAL_SECRET은 백엔드 INTERNAL_API_SECRET과 일치해야 합니다. BASE_URL은 실제 HTTPS 서비스 주소여야 합니다. 키는 브라우저 공개 환경변수로 설정하지 않습니다.
5. WEB을 빌드/배포합니다. 공개 상품 GET만 비로그인 접근이 가능하며, 주문과 이용권은 본인 로그인 자격으로 조회합니다. TEST_ALLOWLIST 계정은 허용된 상품에만 구매 버튼이 표시됩니다. 현재 커버와 그 위의 출시 안내는 사용자 요청에 따라 주석으로 보존하여 일시 해제했습니다. 커버 해제 자체는 판매를 활성화하지 않습니다. 전체 검증 후 커버를 복원하고 일반 계정으로 확인합니다.
6. 아래 실제 거래 검증을 마친 뒤 CLOSED로 되돌립니다. 출시 때 OPEN으로 수동 변경합니다. 자동으로 특정 날짜에 판매를 시작하지 않습니다.

## 결제 경로

- 공개 카탈로그: Backend GET `/api/subscription/plans` (기존 경로 확장).
- WEB POST `/api/passes/orders` → Backend POST `/api/passes/orders` → 저장된 주문 가격으로 PayApp `payrequest`.
- WEB POST `/api/passes/webhook` → 내부 인증된 Backend POST `/api/billing/passes/events`.
- 결과: `/pricing/success?orderId=...`에서 본인 주문 GET을 조회합니다. URL 진입만으로 완료를 표시하거나 자동 이동하지 않습니다.
- 백엔드 POST `/api/billing/passes/link`, `/events`, `/retry`는 X-Internal-Secret 검증을 거칩니다. 이 비밀키를 브라우저에 전달하지 않습니다.
- 가격·이름·기간은 DB 조회값과 주문 스냅샷을 사용합니다. 표시 후 상품이 바뀌면 409 응답으로 새 정보를 확인하도록 합니다.
- 같은 사용자와 중복 요청 키는 한 주문만 생성합니다. PG 요청 결과가 불명확하면 REVIEW에 두며 자동으로 두 번째 결제를 만들지 않습니다. 관리자에게 주문번호로 PayApp 거래 생성 여부를 확인하도록 안내합니다.

## 기존 기능 보존

기존 정기등록/해지 함수, 카드 컴포넌트, 기존 결제 조회·취소·통보 경로는 보존했습니다. 기존 내부 WEB 빌링 중계에는 호출자 인증을 추가했습니다. `/api/payments/create`의 이전 정기등록 구현은 보존하되 공개 호출은 410으로 거부합니다. 새 구매는 `/api/passes/orders`를 사용합니다. 이전 상품 삭제 후 브라우저가 임의 금액으로 정기결제를 만드는 우회 경로를 남겨두지 않기 위한 변경입니다.

기존 `/api/payment` 통보도 연동 KEY/VALUE를 확인합니다. 기존 정기결제 후속 처리 로직 자체는 재설계하지 않았습니다. 새 주문은 이 경로에 의존하지 않습니다.

새 이용권은 기존 유효 유료 구독 뒤에 연결됩니다. 새 권한은 신규 유료 제작/자막 처리 시 확인하며, 이미 접수한 작업의 콜백·완성본 조회/다운로드는 그대로입니다. AI 프로젝트는 수정하지 않았습니다.

## 통보·복구

[PayApp 공식 문서](https://docs.payapp.kr/dev_center01.html)의 일회성 REST, feedbackurl 규격을 따릅니다. 결제 수단은 제한하지 않아 가맹점에서 허용한 수단을 사용합니다. 가상계좌 대기는 권한을 부여하지 않습니다. 가격 검증은 원주문 스냅샷 기준입니다. 부분 취소는 `orig_mul_no`/`orig_price`로 원거래를 대조하고 부분 취소 거래번호·금액을 별도 이벤트에 남깁니다. 부분 취소 금액으로 이용기간을 자동 차감하지 않습니다.

인증된 통보는 이벤트에 먼저 저장하고, 결제 상태 변경과 이용권 부여/회수는 하나의 트랜잭션으로 처리합니다. 실패는 FAILED 이벤트로 남기고 성공 ACK를 보내지 않습니다. PayApp 재시도 종료 후에도 내부 인증 POST `/api/billing/passes/retry`로 RECEIVED/FAILED 이벤트를 최대 100건 재처리할 수 있습니다. 이 요청은 새 PayApp 결제를 생성하지 않습니다. 반복 실패는 원금액·거래번호 및 장애 원인을 확인한 뒤 처리합니다.

판매 중지 자체가 이미 발급한 외부 결제 링크를 취소하지는 않습니다. CLOSED 전환 전후에 PayApp 관리자 화면에서 미결제 요청·가상계좌를 확인하고 필요한 요청을 취소합니다. 그동안 결제/환불 통보 수신은 계속 열어둡니다. 확인된 늦은 입금 통보는 수신 당시 이용권을 부여합니다.

탈퇴 시 새 주문의 사용자 연결만 NULL로 해제됩니다. 새 주문·이벤트는 보존되며, 탈퇴 후 결제 통보로 계정을 다시 만들거나 이용권을 부여하지 않습니다. 해당 거래는 관리자가 PayApp에서 확인/환불할 수 있습니다. 기존 탈퇴 처리 경로와 예전 기록 삭제 정책은 바꾸지 않았습니다.

## 실제 거래 검증 (실행 필요)

개발 환경에서는 신규 테이블 생성·테스트 계정 구매 진행 및 아래 4단계의 PayApp 결제창 진입까지 확인했습니다. 결제 통보가 실제로 전달·처리되는지는 아직 검증하지 않았습니다. 이어서 결제창의 승인 예정 금액을 확인하고 사용자가 직접 결제하는 단계부터 진행합니다. 실제 승인 이후의 5~8단계는 아직 완료되지 않았습니다.

### 1주일 체험권 1,000원 테스트 순서

1. 신규 주문 테이블 적용을 확인하고, 백엔드 실행 환경에 `PASS_SALES_MODE=TEST_ALLOWLIST`, `PASS_TEST_USER_IDS=테스트할 계정의 숫자 ID`, `PASS_TEST_PRODUCT_CODES=PASS_7D`를 설정한 뒤 백엔드를 재시작합니다. 이 값은 WEB의 `.env.local`에 넣는 설정이 아닙니다.
2. WEB의 PayApp 설정과 내부 인증키, `NEXT_PUBLIC_BASE_URL`을 확인합니다. PayApp이 접근할 수 있는 공개 HTTPS 주소의 `/api/passes/webhook`으로 통보를 받을 수 있어야 합니다. `localhost`만으로는 외부 결제 통보를 받을 수 없습니다. 로컬 테스트라면 공개 HTTPS 주소가 해당 WEB 서버로 연결되도록 준비하고, 그 주소에서 로그인부터 진행합니다. 환경변수 변경 후 WEB도 재시작합니다.
3. 허용한 계정으로 로그인하고 `/pricing`을 새로고침합니다. 1주일 체험권의 DB 가격이 1,000원인지, 해당 상품만 `구매하기`로 표시되는지 확인합니다. 버튼이 계속 비활성이면 로그인 계정 ID와 백엔드 재시작 여부를 먼저 확인합니다.
4. 구매 버튼을 눌러 상품명·1,000원·7일·자동갱신 없음을 확인하고 휴대전화번호를 입력합니다. 결제 진행 후 열린 PayApp 화면에서도 승인 예정 금액이 1,000원인지 확인한 뒤 사용자가 직접 결제합니다. 실제 승인되는 거래입니다.
5. 서비스 결과 화면에서 서버가 확인한 결제 완료를 확인합니다. 확인 지연이나 오류가 나오면 같은 결제를 다시 만들지 말고 PayApp 승인 내역과 주문번호를 확인합니다. 가상계좌를 선택했다면 입금 전에는 입금 대기이며, 이용권이 아직 부여되지 않아야 합니다.
6. `/plan`에서 시작·종료 시각을 확인합니다. 기존 유료 이용기간이 없다면 서버 반영 시점부터 한국 시간 기준 7일입니다. 기존 유효 기간이 있으면 그 뒤에 예약됩니다. `/plan/payments`에는 실제 결제한 1,000원이 기록되어야 합니다.
7. 환불 테스트는 PayApp 관리자에서 해당 거래를 전액 취소한 뒤 서비스의 환불 표시와 남은 이용기간 회수를 확인합니다. 부분 환불은 별도의 확인 필요 상태로 기록되며 기간은 자동 변경하지 않습니다.
8. 테스트 종료 후 `PASS_SALES_MODE=CLOSED`로 복원하고 백엔드를 재시작합니다. 발급된 미결제 링크도 PayApp에서 확인합니다. 사용자가 DB의 `sale_price`를 4,900원으로 복원하고 페이지를 새로 조회합니다. 이미 생성한 주문과 결제 내역의 1,000원은 바뀌지 않아야 합니다.

### 추가 검증

- 지정 계정으로 카드 승인·실패·가상계좌 발급·입금 완료를 확인합니다. PayApp 승인액, 주문 price, paid_at, grant 시작/종료가 일치해야 합니다.
- 관리자 전액 환불 후 해당 구매의 남은 기간이 회수되고 예약 이용권 시작/종료가 앞으로 이동하는지 확인합니다. 부분 환불은 확인 필요로 표시되며 기간은 그대로여야 합니다.
- 동일 통보 재전송, PG 응답 유실, 상태 조회 오류, 만료 직전/직후 신규 제작, 기존 작업 완료를 확인합니다.
- FREE 가입과 이전 Basic/Pro/Master 표시, 과거 결제 조회, 회원 탈퇴를 확인합니다.
- 테스트 중 생성한 미결제 링크를 정리하고 CLOSED/커버 상태를 일반 계정에서 확인합니다.

## 되돌리기

우선 판매를 CLOSED로 전환합니다. 상품 DB는 이미 PASS_*로 교체되었으므로 FREE/BASIC/PRO/MASTER만 해석하는 예전 백엔드로 되돌리면 안 됩니다. 신규 상품 코드를 지원하고 새 주문 테이블을 조회하지 않는 호환 버전을 준비한 경우에만, 주문이 없는 상태에서 아래 빈 테이블 전용 SQL을 검토할 수 있습니다. 현재 코드는 새 테이블을 조회하므로 실행 중인 상태에서 테이블을 삭제하지 않습니다. 주문이 한 건이라도 있으면 신규 기록을 삭제하지 않고 통보/재처리 경로를 유지하며 수정 배포합니다. 상품 ID 1~4와 이미 교체한 상품은 되돌리지 않습니다.

```sql
BEGIN;
LOCK TABLE public.pass_orders, public.pass_payment_events, public.pass_grants IN ACCESS EXCLUSIVE MODE;
DO $$ BEGIN
  IF EXISTS (SELECT 1 FROM public.pass_orders)
     OR EXISTS (SELECT 1 FROM public.pass_payment_events)
     OR EXISTS (SELECT 1 FROM public.pass_grants) THEN
    RAISE EXCEPTION '기록이 있어 테이블을 삭제할 수 없습니다.';
  END IF;
END $$;
DROP TABLE public.pass_payment_events;
DROP TABLE public.pass_grants;
DROP TABLE public.pass_orders;
COMMIT;
```
